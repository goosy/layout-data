## 问题描述

spec-layout §5 规定 `register_layout` 每个进程只能调用一次，注册结果存放在模块级的单例里（`registry.js`），布局名在进程的整个生命期内有效。一个进程里所有可注册的布局只能是一个整体。

由此 spec-layout §5 列出的后果都无法绕开：

- 基于 layout-data 的库不能自己调用 `register_layout`，只能导出描述文件路径交给应用合并；两个这样的库若有同名布局或同名片段，应用无法同时使用它们。
- 一个进程里不能有两组互相独立的布局，例如同时模拟两台布局定义不同、布局名却相同的设备。
- 测试无法在同一进程里隔离地注册布局，只能调用内部函数 `register_descriptions`，绕过了公开接口。

## 解决提案

本 issue 依赖 issue#gao82zh3（布局对象化，由布局产生 ldata），要在它实现之后实现。

引入**登记域**（scope，类型 `Layout_Scope`）作为布局名的分隔单位：

- 可以创建多个登记域，每个登记域各有自己的布局和片段，各自可以调用一次 `register_layout`；"每个进程一次"变为"每个登记域一次"，一次注册、整体校验、全部或都不登记的规则在登记域内不变。
- 布局名和片段名只在登记域内唯一，不同登记域里同名互不冲突。
- **没有默认登记域。** 布局只能注册到显式创建的登记域里，应用也要创建自己的登记域；不指定登记域的注册不复存在，全局的 `register_layout` 随之取消。这是破坏性变更：现有的 `register_layout(descriptions)` 要改为先创建登记域、再向它注册，`get_layout(name)` 要改为从登记域取得，`render_types(layouts, options)` 要改为登记域的类型生成，`new Ldata` 的按名引用要改为带登记域名的引用。
- 登记域名在创建登记域时给出，和布局名一样必须是 JavaScript 的标识符（spec-layout §4），所以不含 `.`，引用可以无歧义地拆开；包名这类含 `@`、`/`、`-` 的字符串不能直接用作登记域名。登记域名在进程内唯一，由创建它的库或应用负责选择，重名时创建登记域报错。
- 登记域可以查询和获取：按登记域名可以取得已创建的登记域，在登记域上注册、按布局名取得布局。全局的 `register_layout` 和 `get_layout` 都不再提供，注册和取得布局只经过登记域。`new Ldata` 以布局对象为常规写法，例如 `new Ldata(scope.get_layout("Pump"), "pump_1")`：布局对象本身属于某个登记域，错误出现在从登记域取得布局的那一步，取得的布局还可以交给 `io_index_table` 等其他接口。只有必须用字符串指出布局的地方，即 `new Ldata`，还接受带登记域名的引用 `登记域名.布局名`，例如 `new Ldata("lib_a.Pump", "pump_1")`，这是不必先取得布局就能建立 ldata 的便利写法，适合引用来自配置文件这类场合。它只是引用，布局名仍是 `Pump`。没有默认登记域，所以不带登记域名的引用不指向任何布局。`new Ldata` 不增加参数。

这样做的主要收益是让基于 layout-data 的库能自带并自己注册布局，应用可以在同一进程里组合多个这样的库；同名布局互不冲突是隔离的推论，不是单独的理由。取消默认登记域，是因为它是一份全进程共享、只能用一次的资源：哪个库违反约定先用了它，应用自己的注册就会失败，结果还取决于 import 的先后，而"库不得使用默认登记域"只能是约定，无法强制。没有默认登记域，每一方都必须用自己的登记域，彼此的布局不会侵入，实现和规范也不再有默认登记域这个特例。由此有以下设计要求：

- 布局的身份由布局对象确定，不再由布局名确定：§2.1 中"布局名在进程的整个生命期内标识唯一的布局，同一布局的数据块共用一个类"要改为按布局对象区分，内部按布局名缓存的类也要改为按布局对象缓存。
- 登记域可以按名获取，所以任何模块都能取得别的库或应用的登记域，也能向它注册。本包只提供基础设施，不规定谁可以向哪个登记域注册：冲突只由"每个登记域只注册一次"保证，第二次注册总是报错。库要防止自己的布局被别人决定，就在创建登记域时立即注册；库也可以把登记域留给使用方注册，例如让使用方在库的描述之外补充自己的布局。库与使用方如何交互、如何避免冲突，由库自行约定。
- 类型生成（spec-layout §8）改为登记域的方法，不再是全局的 `render_types`：它为登记域的全部布局生成一份声明文本，不再接收布局表，也不支持只为部分布局生成；声明只供编辑器读取类型，多出来的类型无害。它以布局名生成 `<布局>_Tags`、`<布局>_Ldata`，所以不同登记域的同名布局生成同名的类型；按登记域生成，正好一个登记域一个文件，由 import 路径区分，规范要说明这种用法。
- 诊断信息要能区分登记域：`unknown layout X` 等错误和日志只给出布局名时，分不清是哪个登记域的布局，错误和日志要用引用写出布局（如 `unknown layout lib_a.Pump`）。`Ldata.on_access` 的观察者如果按布局名归类，也会把不同登记域的同名布局混在一起，规范要提醒这一点。
- 注册失败不会用掉登记域的这一次调用，可以在同一登记域重试。
- 测试改为在各自的登记域里注册，走公开接口，不再调用内部函数。

命名：公开的单位按使用者需要理解的含义命名，即名字在其中有效、彼此隔离的范围。中文叫登记域，与 spec 中"已登记的布局"一致；英文叫 scope，导出类型按本包的习惯加前缀，叫 `Layout_Scope`。创建、获取登记域和向它注册的具体接口由 design 决定。registry 一词留给实现层，指存放注册结果的场所（`registry.js`）。登记域在本 issue 被接受之后才列入 spec 的术语。

否决的方案：

- 取消"只注册一次"、允许多次调用：会让布局与片段的解析依赖调用顺序，正是 spec-layout §5 一次注册所要避免的。
- 把前缀写进布局名本身（如把布局命名为 `Lib_Pump`）来区分：只是约定，无法隔离片段解析，也不能让同一名字在不同组里各自注册。`登记域名.布局名` 不同，它是对真实登记域的引用，布局名本身不变。
- 保留全局默认登记域，供不指定登记域的调用使用：兼容现有用法，单个应用也少写一步，但它是只能用一次的共享资源，"库不得使用"只能靠约定，而且要在实现和规范里为它保留特例。
- 每个模块一个默认登记域：只能靠调用栈之类的手段识别调用者，打包后模块边界不复存在；一个库也由多个模块组成，按模块分开会把库自己的布局拆散。
- 只允许创建登记域的一方向它注册：要引入所有者之类的概念，也排除了让使用方决定注册时机、补充布局的用法；需要保护的库提前注册就够了。
- 匿名登记域，不进全局名字表，只按对象持有：隔离最强，但登记域无法按名查询和获取，引用也不能写在配置文件里。
- 保留全局的 `get_layout` 来解析带登记域名的引用：需要布局对象时可以从登记域取得，引用只有创建数据块时才必须用字符串写出，保留它只是多一个全局入口。
- 只用对象引用（给 `get_layout` 和 `new Ldata` 增加指定登记域的参数）：要增加接口，引用也不能写在配置文件这类字符串里。
- 公开的单位叫 registry（登记表）：registry 既指注册的场所，又指名字的分隔单位，用作公开名会把实现层的含义带给使用者。
- 叫 registry scope：同样把实现层的 registry 带进公开接口，而且名字冗长。
- 叫 space（命名空间）：命名空间暗示名字有层级或前缀，容易与上面否决的前缀方案混淆。
