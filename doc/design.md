## 2. Parts

| Part | Responsibility | Instances | Mutability |
| --- | --- | --- | --- |
| Layout | Compiled from an item table listed in `layouts`: the public `name`, `length`, `size`, `items` and the methods `create_ldata`, `get_ldata`, `delete_ldata`, `io_index_table`; the private compiled data (byte position and codec of every tag, a byte-to-tag lookup table), the Ldata subclass of the layout and the table holding its ldata by name | One unbound per layout of a description; one bound per structure in every scope | The public part immutable, the ldata table mutable |
| Ldata | The value buffer (private, big-endian), access by name, raw read and write methods, the Ltag returned by `get(name)` | One per ldata | Mutable |
| Observer | Snapshot comparison, emits change events | One per ldata | Mutable |

Dependency direction: Layout depends on the description and on Ldata (it builds the subclass and creates ldata); Ldata uses the layout and the compiled data that Layout hands it when the subclass is built, and `Ldata.js` does not import `layout.js`, so there is no cycle; the Observer uses only the buffer and the compiled data that Ldata hands it. The user's scheduling and IO are outside the package; the package notifies them only through the `write` event of an Ldata, which any party can listen to.

### 2.1 Component boundary

- The package code does not depend on the user's configuration, business logic or logger;
- Errors are thrown as exceptions; nothing is logged and `process.exit` is never called;
- Descriptions are external input to the package: the user gives YAML text or description files, which `yaml` and `desc_file` read and compile. Reading files, parsing and compiling are apart from registration, which takes the compiled `Description`s only.

### 2.2 Boundary of the development entry and the command line

The development entry `layout-data/dev` (`src/dev.js`) and the command line `layout-types` are used at development time only, and have nothing to do with the run time of the application:

- Their input is descriptions only and their output is declaration text only. They take, return and read no run-time object of the application (scopes, layouts, ldata);
- They run in the developer's own process (a development script or the command line), and create neither scopes nor ldata;
- The run-time entry `layout-data` (`src/index.js`) does not import `dev.js`, so the application does not load the code that renders types; `dev.js` uses the run-time implementation only through `desc_file`, `check_scope_name` of `scope.js`, and `check_descriptions` and `plan_layouts` of `layout.js`, so the rules of reading, validation and layout conflicts are exactly those of the run time;
- The text always imports `Ldata` from `"layout-data"`: it is read by the editor of the developer's project, which depends on this package. How the application bundles its run-time code has nothing to do with rendering the types;
- The command line is an argument shell around the same function: it parses the arguments and calls `render_types`, with the same input and result, except that it takes description files only and reads them with `desc_file`.

## 3. Descriptions and registration

The public terms (description, description file, `Description`, item table, layout, scope, block) are those of spec.md §2. Reading and registration pass through stages whose products are internal; this document names them:

| Term | Meaning | In the code |
| --- | --- | --- |
| Source | One description of the name space of a description: its origin (a file path or `YAML text`) and its parsed root | An element `{ origin, root }` of the list `load_imports` returns, the first being the description read itself |
| Item table cache | The item tables reached, by item table name, with their references resolved | `tables` of `compile_description` |
| Structure | An item table listed in `layouts`, with its references resolved and expanded into flat items | `Data_Struct`, made by `build_structure` |
| Compiled data | What `Ldata` needs of a layout and the public Layout does not show: `entries` and `tags_at_byte` | `Compiled_Layout`, the private field `#compiled` of Layout |
| Fingerprint | The canonical text of the compiled structure of a layout: the name, lower case type, offset and initial value of each tag, in layout order | What `fingerprint(items)` returns |

**Reading.**

- `yaml.js` reads descriptions (spec-description.md §1.1). `yaml(...args)` and `desc_file(...args)` take either a template call, whose first argument is an array with `raw`, or one plain argument. A template call is joined into one string by `String.raw`. `yaml` takes the text; `desc_file` takes a string or a `URL` (the path of a URL is `fileURLToPath(url)`, which also rejects a URL that is not `file:`) and reads it with `readFileSync(path, "utf8")`. Anything else throws `TypeError`. YAML is always parsed with `parseDocument(text, { version: "1.2" })`, the result being `doc.toJS()`.
- `load_imports` starts from the description read and reads its `imports` depth first, returning all the sources of the name space. The origin of the description read is the path `desc_file` got, or `YAML text`; its directory (the text of `yaml` has none) resolves relative paths. Every imported path: one starting with `file:` is converted by `fileURLToPath`, an absolute path is used as it is, a relative path is resolved by `path.resolve` against the directory of the importing file, and a relative path in the text of `yaml` is an error. An imported file is known and named by its resolved absolute path: a path already read is not read again, so a file counts once; a path already on the current chain of imports is reported as a cycle (`b: circular import a -> b -> a`, written by the importing file `b`). A root that is not a mapping, an `imports` that is not a list of strings, and a file that cannot be read or parsed go to the list of errors with the origin, every read and parse error starting with the path of the file. Of an imported description only `imports` and `item_tables` are read; `layouts` and `blocks` are neither read nor checked.
- The sources go to `compile_description(sources, errors)` of `layout.js` (below), and its result to `make_description`. On any error `yaml.js` throws an `Error` with `errors`, titled `invalid YAML text` or `invalid description file <path>`; otherwise it returns the `Description`.

**Compiling.** `compile_description(sources, errors)` does all the work that does not depend on a scope, pushing problems to `errors`. It returns the intermediate value of the processing of a description, `desc_process`: the root object parsed from the description read, with `layouts` replaced by the result of the compilation and `blocks` made `[]` when absent, that is `{ ...root, layouts, blocks }`. The intermediate value is passed on as `{ ...desc_process, <the keys replaced> }`, every step handling only the keys it replaces and ignoring the others, so the other root keys reach the `Description` as they are:

- The `layouts` of the description read must be a list of strings; a name repeated or not matching `IDENTIFIER` (`structure.js`) is an error. The `item_tables` of every source (an empty mapping when it has none) must be a mapping.
- From every name of `layouts`, `resolve_table` traverses the item tables (spec-description.md §4): a name is looked up in the `item_tables` of all the sources, and one not found, one found in two sources (naming both origins) or one whose value is not a list is an error; a name already on the current chain of references is reported as a cycle. `resolve_items` resolves the references of `includes` and `coupling` in one list and fills in the omitted `length`s; it copies every item and nested list. Every item table is resolved once and kept in the item table cache, so an item table referenced many times reports its errors once; a reference gets a deep copy of the cached one (`structuredClone`), so expanding it changes neither the cache nor another reference. Item tables not reached are neither read nor compared.
- Then, for every layout, it calls `build_structure` on a deep copy of its cached item table to expand it into flat `items` (computing the total `length` of the structure and normalizing `coupling` to an array of names), validates it with `validate_structure` (§3.1), and when all are valid compiles each into a Layout not bound to a scope with `compile_structure`.
- `blocks` is first made `[]` when absent (`undefined`), then checked: it must be a list of mappings, whose `name` is a string unique within the description and whose `layout` matches `<IDENTIFIER>.<IDENTIFIER>`; a block in error is named by its name or position (`block #i`), after the origin of the description read (none for `YAML text`). `check_blocks` only checks, returning nothing and copying no block: the parsed list itself stays in `desc_process` and is frozen with the `Description` at the end.
- Without errors `make_description(desc_process, path)` builds the `Description`: `{ ...desc_process }`, where `layouts` maps the layout names to the unbound layouts (in the order of `layouts`), `blocks` is the parsed list of blocks, the other root keys hold the parsed values, and the whole is deeply frozen. The root object is made by `doc.toJS()` for this reading only, so freezing it in place affects no caller. The root keys of imported descriptions are not merged in. It carries two properties that are not enumerable, both keyed in `internal.js`: `DESCRIPTION` (the value `true`), which tells that `yaml` or `desc_file` made it, and, for one read by `desc_file`, `ORIGIN`, the path. Both keys are Symbols registered with `Symbol.for(...)`, not Symbols of their own, because each entry is bundled with a copy of `yaml.js` and `layout.js` (§7): a `Description` made by `desc_file` of `layout-data` is passed to `render_types` of `layout-data/dev`, and both copies must read the same keys.
- Fields and types of items: every tag item has `{ name, type, offset }` and optionally `length`, `init_value` and `comment`; `offset` and `length` are in bits, and when `length` is omitted the type decides it. `type` values (case-insensitive): `Bool`, `Byte`, `SInt`, `USInt`, `Int`, `UInt`, `Word`, `DInt`, `UDInt`, `DWord`, `Real`. A `Word` item with `coupling` (an item table name or an inline list) is a status or command word made of several Bools. `is_combined: true` is a descriptive mark only: the word and its bits share the same bytes, so the linkage does not depend on it. The `offset` of each item in `coupling` is relative to the start of the word. `{ includes: <item table name or inline list>, offset }` splices in a group of common items shifted as a whole; `name_prefix` may be added. The types of items (`Tag_Item`, `Include_Item`, `Layout_Item`) are in `internal_types.js` and not public.
- Only one side of a combined word and its bits gives `init_value`. When `build_structure` expands them, a word without a value is composed from its bits (a bit without a value is false), and a word with a value passes its bits' values down; if neither side gives one, they are left without one. If both sides give values, the given values are kept and validation reports the conflict.

**Layout.**

- `Layout` is a class of `layout.js` whose instances are deeply frozen (the constructor ends with `Object.freeze(this)`); its only public properties are `name`, `length`, `size` and `items`, with the read-only `scope` on the prototype (spec-layout.md §4), where `items` are frozen copies of the expanded items with only the documented fields. The methods `create_ldata`, `get_ldata`, `delete_ldata` and `io_index_table` are on the prototype, so `{ ...layout }` copies the four properties only. The compiled data, the table `entries` indexed by name (byte offset, bit mask, codec) and the byte-to-tag lookup table `tags_at_byte`, is kept in the private field `#compiled` and is never a property, so no entry appears in the public interface.
- The constructor is `(key, name, length, items, compiled, scope)` and requires the key `CREATE_KEY`, private to `layout.js`, throwing `TypeError` otherwise, so layouts are made only by compiling and registering, and `new layout.constructor(...)` fails too. In the declarations the constructor is private (JSDoc `@private`); the `Layout` of `typedefs.js` refers to this class and `Layout_Desc` is `Omit<Layout, "scope">`, and the package exports the types only, not the class.
- An unbound layout is made by `compile_structure(data_struct)`, its `scope` being `undefined`. `bind_layout(desc, scope)` binds one: it constructs a new Layout from the `name`, `length`, `items` and compiled data of the unbound layout (read through the Symbol-keyed read-only getter `layout[COMPILED]`, the key in `internal.js`), with this scope as `scope`. The frozen `items` and the compiled data never change, so the layouts bound from one unbound layout share them; every bound layout has its own private state (the Ldata subclass, the ldata table). `scope` is a getter of the private field `#scope`; a scope object is not a property of the frozen object, so it is kept in a private field.
- When a bound Layout is constructed it calls the Symbol-keyed static method `Ldata[LDATA_FACTORY](layout, compiled)` (the key is in `internal.js`), which builds the Ldata subclass of the layout (§4) and returns the function that creates its ldata; the layout keeps the function in the private field `#create_ldata`. An unbound layout builds no subclass, its `#create_ldata` is `null`, and `create_ldata` throws `Error` (`layout X is not bound to a scope`). The subclass and the key `CREATE_KEY` never leave `Ldata.js`: the layout knows only the creating function. `io_index_table(endian)` hands `size` and `#compiled` to the internal function of the same name in `endian.js` (§6). The tag accessors read and write the private buffer of `Ldata`, so the subclass is built inside the class body of `Ldata`; the static method is in the class body too, so it reaches the private members directly, with no static initialization block or module variable to relay them, and a Symbol key never meets a tag name (spec-data-api.md §2.10); `layout.js` depends on `Ldata.js`, and `Ldata.js` does not depend on `layout.js`.
- The ldata table of a layout is the private field `#ldata`, a `Map<string, Ldata>` holding ordinary strong references. `create_ldata(name)` throws `ldata X.Y.Z already exists` when `name` is a string already in the table, and otherwise calls the creating function (which checks that `name` is a string, `TypeError`), puts the result in the table and returns it. `get_ldata(name)` looks the table up and throws `unknown ldata X.Y.Z` when the name is not there; `delete_ldata(name)` returns `this.#ldata.delete(name)`. An ldata does not know the table, so unbinding it does not affect it.
- `fingerprint(items)` computes the fingerprint from the public `items`: in order, the `name`, the lower case `type`, the `offset` and the `init_value` (`null` when absent) of every tag; the text `JSON.stringify` makes of them is the fingerprint, used as a `Map` key as it is, with no hash. The bits of a combined word follow from the offsets (the combined word rules of §3.1) and `length` from the type, so neither is counted. It reads public members only, so it works on a layout compiled by the other bundle too (`render_types`).

**Scopes and registration.**

- A scope (spec-layout.md §2) is the class `Layout_Scope` of `scope.js`. `create_scope(name)` checks the name with `check_scope_name(name)` (`TypeError` for a name that is not a string, `Error` for one that does not match `IDENTIFIER`) and then constructs the scope with the key `CREATE_KEY`, private to the module; the constructor throws `TypeError` without the key, is private in the declarations, and `Layout_Scope` of `typedefs.js` names the class, which the package exports as a type only. The constructor takes the name in the registry with `add_scope` of `registry.js` (`Error` for a name in use) and ends with `Object.freeze(this)`: a scope can be got by its name, and freezing keeps the module that gets it from replacing its methods or redefining `name`. `get_scope(name)` gets the scope from the registry and returns `undefined` when there is none.
- The registry (`registry.js`, which imports nothing) keeps the scopes by scope name, for `get_scope` and the uniqueness of the names only; the layout table of every scope is kept in another table keyed by the scope object, and has two `Map`s: `by_name`, by layout name, and `by_fingerprint`, by fingerprint. `layouts_of(scope)` finds it by the object itself, never by the name, so an object that reads with the same name reaches no other scope's layout table, a guarantee beside the freezing. `scope.js` writes the scopes, `layout.js` the layouts, and `get_layout` of a scope reads them. The registry is never cleared: the scopes and their layouts last for the life of the process.
- `register_layout(descriptions)` of a scope calls the internal function `register_descriptions(descriptions, scope)` of `layout.js`, any number of times. The tests register many times in one process, usually each time in a scope of its own (`fresh_scope` of `test/api/share.js`), through the public interface.
- `register_descriptions(descriptions, scope)` first checks its argument: an empty list, a list inside the list and a value without the mark `DESCRIPTION` are errors, the last telling to use `yaml` or `desc_file`. The origin of every description is its `ORIGIN`, or else `description #i` for the i-th of a list (`description` for a single one). Then it takes three steps, the first two only checking and changing nothing:
  1. **Layouts.** `plan_layouts(list, existing, errors)` takes every unbound layout in the order of the list, computes its fingerprint and looks it up in the staging table and in `by_fingerprint` of the scope: found under the same name, it is reused (the layout the scope has, or the one staged in this call), and under another name it is an error; not found, a name in the staging table or in `by_name` of the scope is an error, and otherwise `bind_layout` makes a new layout bound to this scope and stages it. The result is the layouts of the call, by name, and the layouts to be registered;
  2. **Blocks.** The blocks of all the descriptions are gathered, a block name repeated in the call being an error naming both origins. Every block is split at the `.` into a scope name and a layout name: for this scope the layout is looked up in the staging table and then in the scope, and for another one the scope is found with `find_scope` and the layout in its layout table; no scope or no layout is an error. A layout that has an ldata of the block name is an error;
  3. **Taking effect.** On any error it throws an `Error` with `errors`, titled with the scope name (`invalid layout descriptions of scope X`), having changed nothing. Otherwise it writes the new layouts in the two tables of the scope, calls `create_ldata(name)` of the layout of every block, and returns `{ layouts, ldata }`. The block names are checked to be free and the initial values of the tags were validated, so this step cannot fail, and the scope is never left half done.
- `register_structure(data_struct, scope)` compiles a structure and registers it in a scope directly, with neither validation nor fingerprint comparison; only the test helper `one_tag` calls it, to pad a data block freely, and it throws `another layout is already named X.Y` for a name the scope uses. No other path registers a layout that has not been validated.
- `get_layout(name)` of a scope returns the layout of the scope and throws `unknown layout X.Y` when there is none. Errors name a layout as `<scope>.<layout>`: the class name of the subclass (`Ldata_X.Y`), the error of a reserved tag name, the oscillation error of the Observer, and `X.Y.Z` of an ldata.
- Bool placement: `byte = offset >> 3`, `bit = offset % 8`. The internal buffer is big-endian and the first byte of a word is the high byte of the register, so offsets 8-15 in `coupling` are register bit 0-7 and offsets 0-7 are register bit 8-15. Listing the bits in the order 8-15, 0-7 in the layout file therefore lists them from register bit 0 to bit 15.

### 3.1 Layout validation

The layout rules are validated centrally at the layout stage, not spread over the run time of Ldata and Ltag:

- `validate_structure(data_struct)` validates the flat `items` produced by `build_structure` and returns an array of violation descriptions (an empty array means valid). It does not stop at the first error. It is internal.
- What it checks:
  - Names: a name that is not a string matching `TAG_NAME` (`/^[A-Za-z_][A-Za-z0-9_]*$/`: the ASCII identifier that every language and PLC accepts; so a number of YAML, an empty or a missing name fails here); duplicate names in `items`; names colliding with a member of Ldata (methods and getters on `Ldata.prototype`, and instance fields such as `name`).
  - Type and length: `type` is not a supported type; `length` does not match the type (Bool 1, Byte / SInt / USInt 8, Int / UInt / Word 16, DInt / UDInt / DWord / Real 32).
  - Alignment: the `offset` of a non-Bool must be a multiple of 8; the byte offset of a multi-byte type must be even.
  - Overlap: non-Bool items are sorted by byte range and neighbouring ranges are checked for intersection; Bools are checked by `offset` for a bit occupied twice; a Bool inside the range of a non-Bool requires the `coupling` of that Bool entry (after expansion, the array of names of the combined words it belongs to) to contain the name of the non-Bool entry.
  - Combined words: every bit named in the `coupling` of an item must exist, be a Bool, and have an `offset` within `[offset, offset + length)`.
  - Total length: `length % 16 === 0`.
  - A given `init_value` matches `type` in type and range; a tag without one is not checked.
  - A combined word and its bits do not both give `init_value` (the conflict is recorded during expansion and reported by validation).
- `build_structure` keeps items with duplicate or invalid names and leaves them to validation. An item is dropped only when it is a pure inclusion (it has `includes` and no name); any other item is a tag, so a tag item without a name is reported and not lost. A name prefix is put only before a name that is a string.
- `compile_description` validates all the layouts of a description and, on violations, `yaml` or `desc_file` throws an error that contains all of them (`error.errors`).
- After validation passes, Ldata and Ltag do not repeat these checks; `register_structure` keeps only defensive assertions.

## 4. Codecs and prototype accessors

- The codec table `codecs.js` has one entry per type: `get(buffer, byte, mask)` decodes from the big-endian buffer and `set(buffer, byte, mask, value)` encodes into it. Device byte order is not handled in the table.
- Every layout builds one Ldata subclass when it is compiled (`Ldata.#build_class(layout, compiled)`, which the static method `Ldata[LDATA_FACTORY]` calls) and defines the accessor of every entry once on its prototype, shared by all instances of the layout. The subclass is held only by the creating function that its Layout keeps privately (§3); `Ldata.js` does not index subclasses by name. The constructor of the subclass is `(key, name)` and hands the layout and the compiled data it belongs to on to `super` (§5); it has no public static members. The accessors:
  - the getter decodes from `buffer` with the codec on every read and caches nothing;
  - the setter writes into `buffer` with the codec and then calls `after_write`.
- A combined word and its bits share the same bytes, so writing either one makes the other read the new value; no extra linkage is needed.
- A tag name must not be a reserved name (spec-data-api.md §2.10), as its accessor would shadow a member. The reserved names are the static set in `reserved.js`: the members of Ldata, the method and field names of EventEmitter in Node.js 20.11 and the names of `Object.prototype`. Nothing is probed at run time, so the set does not depend on the Node.js version. `reserved.js` exports `is_reserved_name(name)` to `structure.js` and `Ldata.js` only; the package does not export it and Ldata has no static method for it. `validate_structure` reports a reserved name, and `Ldata` throws when it builds the subclass. A test compares the set with the names found on an instance in the running Node.js, so a new EventEmitter member makes the test fail and the set is then extended.
- The reserved event names (`change`, `write`, `read`) are the constant `RESERVED_EVENTS` in `reserved.js`, for the tests and the documentation; they are a rule for the user and are not enforced at run time. `Ldata` and `Ltag` override `on`, `once` and `off` (each calls the `EventEmitter` method) only to carry the typed overloads: a listener type chosen by the event name through the conditional types `Data_Listener<E>` and `Tag_Listener<E>` of `typedefs.js`, so that a wrong listener of `change` or `write` is a compile-time error and other names take any listener. From 1.0 on, future members of Ldata are `Symbol`-keyed or static.
- The `access` event (spec-data-api.md §2.8) has two kinds of listener. The instance listeners are those of the `EventEmitter` of the data block; the class listeners are kept apart in a module-private `Set` of `Ldata.js` (`Ldata.on_access` and `Ldata.off_access` add to and delete from it), so that neither `removeAllListeners()` nor any other call on an instance can reach them. Before anything is built, `#has_access_listeners()` tests `class_access_listeners.size > 0 || this.listenerCount("access") > 0`, so a data block without a listener pays one cheap check per access. The instance part is not cached in a flag kept by the `newListener` and `removeListener` events, because `removeAllListeners()` also removes those two internal listeners and the flag would go wrong; the class part is counted by the `Set` itself, which only the two static methods change. `#emit_access(kind, tags, errors)` calls the instance listeners through `emit_all`, then the class listeners (each in its own `try`, with `(this, kind, tags)`), and pushes what they throw to `errors`. The module flag `in_access` is set around both calls and suppresses every access made meanwhile, to any ldata, by the listeners themselves. A read throws `errors[0]` after the listeners, a write passes `errors` on to `#written()`, which emits `access` right after `touch()` and before the detection, and throws the first error at the end, so that the buffer, the snapshot and the events stay consistent. The tags are the handles of `get(name)` (created when first needed): by name, the one tag; for a byte range, `#tags_in(start, end, mask)` walks `tags_at_byte`, leaves out repeats and the Bools whose bit is not in `mask` and sorts by the index of the entry.
- `render_types(descriptions, { scope = "app", source })` of `dev.js` (spec-layout.md §5) first checks the scope name with `check_scope_name(scope)` of `scope.js` (the same exceptions as `create_scope`), creating no scope; then it checks its argument with `check_descriptions` of `layout.js` (as `register_layout` does) and combines the layouts of the descriptions with `plan_layouts` by the rules of registering in one empty scope, binding none, a conflict throwing the same `Error` with `errors` as `register_layout`. Both read only the public members of a `Description` and the two registered Symbol keys `DESCRIPTION` and `ORIGIN`, so a `Description` compiled by `layout-data` is handled by `layout-data/dev` too. Without `source`, when every description has an `ORIGIN` (it was read by `desc_file`), the paths joined by `, ` are the `source`. Then it hands the combined layouts, with the scope name, to the internal function `render_declarations(scope_name, layouts, options)` of `types.js`, which declares per layout an interface `<Layout>_Tags` with a property per tag and the type `<Layout>_Ldata = Ldata & <Layout>_Tags`, reading only `name` and `items` of a layout. The layout name is used as it is, with no case folding (the case style is the caller's choice), so that the type names are those of `scope.get_layout("<Layout>")` and different names in one scope cannot collide. The compilation has checked that the layout names match `IDENTIFIER`, and the validation the tag names, so both are written as they are, with no further check. `IDENTIFIER` uses the Unicode properties `ID_Start` and `ID_Continue` (and `_`, `$`), so that names in any script are accepted. `doc_comment` turns a `comment` into a one-line or a multi-line doc comment and escapes `*/`. The module specifier `Ldata` is imported from is always `"layout-data"`; no `source` gives a header without a file name, and the header comment shows the JSDoc cast that names the type of the value, getting the scope with `get_scope("<scope>")`. `create_ldata` returns the type `Ldata`: the declaration of one method cannot return another type for each layout.
- The command line (spec-layout.md §5.1) is in `dev.js` too. The top level of the module looks at `import.meta.main`:
  - `true` (run as the entry, Node.js >= 24.2): it calls `run_cli(process.argv.slice(2))`, which returns the exit code, set as `process.exitCode`;
  - `undefined` (Node.js before 24.2) and this file is the entry: it writes to the standard error the version required, the version running (`process.version`) and the hint to use the function entry instead, and sets `process.exitCode = 1`. Whether this file is the entry is found by comparing `realpathSync(process.argv[1])` with `import.meta.filename` (a bin of pnpm may go through a symbolic link or a `.cmd` wrapper), for this message only;
  - otherwise (imported): nothing.
- `run_cli(args)` parses the arguments with `parseArgs` of `node:util` (`allowPositionals`, the options `scope`, `out`/`o` and `help`/`h`). An unknown option and no description file are argument errors: it writes the reason and the usage and returns 1. `--help` writes the usage (with the version requirement) to the standard output and returns 0. Otherwise it reads every file with `desc_file`, collecting the `errors` of all the files that fail (the message, for an error without them); when any fails, it writes them to the standard error under `invalid description files`, returns 1 and renders nothing. Then it calls `render_types(descriptions, { scope })`, writes the text to `--out` or the standard output and returns 0. An error thrown by `render_types` goes to the standard error (every item of `errors` when it has them), and it returns 1 and writes no output file. `run_cli` never calls `process.exit`, so the output is flushed before the process ends. It is not exported: the tests run `dev.js` as a child process with `process.execPath`, as a user does, and are skipped on a Node.js without `import.meta.main`.

## 5. Ldata

- An ldata is created only by `layout.create_ldata(name)` (spec-data-api.md §2.1), which calls the creating function returned by `Ldata[LDATA_FACTORY]`: it constructs the subclass of the layout (§4) with the key `CREATE_KEY`, private to `Ldata.js`. The constructor of `Ldata` is `(key, name, layout, compiled)`: before `super()` it checks that `key` is `CREATE_KEY` and throws `TypeError` otherwise (the message is `an ldata is created by its layout: layout.create_ldata(name)`), then that `name` is a string (`TypeError`). So `new Ldata(...)` and `new` on a subclass (such as `data.constructor`) both throw; in the declarations the constructor is private (JSDoc `@private`), so TypeScript allows neither `new` nor `extends`. `Ldata` itself is never the direct class of an instance. The instance allocates `buffer` (`layout.size` bytes) and encodes the `init_value` of the entries in order, skipping an entry without one, which keeps the zeroed bytes.
- `name`, `layout` and `size` are read-only (getter only, assignment throws `TypeError`); `name` is the private field `#name`, which the constructor sets after it has checked, after the private key and before `super()`, that it is a string (`TypeError`). `setMaxListeners(100)` of an Ldata and `setMaxListeners(20)` of an Ltag are fixed in their constructors. The buffer is a private field (`#buffer`) with no accessor, always big-endian; the Observer and the transaction get it from the Ldata that creates them. Typed access goes through tags, untyped access through bytes: there are no raw methods classified by width.
- There are two ways to write the buffer, both through Ldata and allowed at any time:

  | Way | Used by |
  | --- | --- |
  | Assignment by name (`data[name] = v` or `tag.value = v`) | Any code |
  | Raw methods `write_bytes(offset, source)` and `write_bit(offset, mask, value)`, locating by byte offset | Code that deals with register addresses, such as a Modbus server, and the IO layer |

- `read_bytes(offset = 0, length = size - offset)` returns a copy of a byte range (`Buffer.from(buffer.subarray(...))`), so the buffer cannot be changed through it.
- The raw methods check their arguments before touching the buffer, so that on error the data is unchanged and `#written()` is not reached: `offset` and `length` must be integers with `0 <= offset` and `offset + length <= size`, `mask` an integer from 1 to 0xff (`RangeError`), `source` a `Uint8Array` (`TypeError`). `write_bytes` copies with `buffer.set(source, offset)`. A raw write records the byte range it touched for the Observer (§5.1).
- `load_tag(name, io_buffer, endian)` and `store_tag(name, io_buffer, endian)` (spec-data-api.md §2.9) resolve `name` to the compiled entry of the layout (an unknown name throws `Error`), check `endian`, `io_buffer` and the range of the entry in it (`io_range`), and then call `load_entry` / `store_entry` of `endian.js` with the private buffer. `load_tag` registers the byte range of the entry and ends in `#written()` like any write; `store_tag` only reads the buffer. `Ltag.load(io_buffer, endian)` and `Ltag.store(io_buffer, endian)` call them with the name of the tag, so an Ltag needs no check of which ldata it belongs to.

- Ldata throws exceptions on errors (layout conflicts, refused values); it neither logs nor exits.
- **Value checks.** A codec has `check(value)` next to `get` and `set`: it returns `null` for an acceptable value and the reason text otherwise. The setter of a tag accessor calls it before `codec.set`, so a refused value touches neither the buffer nor the observer, and throws `TypeError` when `typeof value` is not `"number"` and `RangeError` when it is (the message is `<ldata name>.<tag>: <reason>`). `Bool` always returns `null`. Integer codecs require a number, `Number.isInteger` and the range of the type; the `Real` codec requires a number, lets `NaN` and `±Infinity` pass and refuses a finite value whose magnitude is above `FLOAT32_MAX` (`3.4028234663852886e38`, the value `check_init_value` of `structure.js` uses). `Buffer.write*` is left as the last defence and is not the check.
- `data.get(name)` returns the `Ltag` of the tag, created and cached on first access; for an unknown name it returns `undefined`. An Ltag holds no value: reading `value` decodes from the buffer of the Ldata, writing `value` is exactly equivalent to `data[name] = v`; `name`, `type` and `size` come from the compiled entry of the layout, which an Ltag holds privately and does not expose; the `change` event is emitted by the Observer.

### 5.1 Detection, transactions and the Observer

Every write path ends in the same private method of Ldata:

```js
#written() {
    if (this.#transaction) { this.#transaction.written = true; return; }  // in a transaction: only remember
    this.#observer.diff();                                                // detect right now
    this.emit("write", this);                                             // then tell the listeners
}
```

- Outside a transaction, `diff()` is called synchronously inside the write statement, then `write` is emitted.
- `diff()` is internal: no public method triggers a detection. Every write path reaches it through `#written()`, so the buffer never differs from the snapshot outside a write or a transaction.

**Transactions.** `transaction(fn)` throws `Error` if a transaction is already open; otherwise it copies the buffer, registers the transaction state `{ written: false, read: Set, write: Set }` and calls `fn()` synchronously:

- Accesses: inside a transaction `#emit_access` adds the tags to the `read` or `write` set of the state instead of calling the listeners. It is reached only when `#has_access_listeners()` was true, and it returns first while `in_access` is set, so nothing is gathered without a listener or during a listener. `#in_layout_order(tags)` sorts a set by the index of the entries at the end;
- `fn` returns normally: the transaction is closed, the gathered `access` of kind `read` and then of kind `write` is emitted, `diff()` is called once, one `write` is emitted if `written` is true, and the return value of `fn` is returned (it is not checked for being a Promise);
- `fn` throws: the transaction is closed, the copy is written back to the buffer, only the gathered `access` of kind `read` is emitted (what its listeners throw is dropped), and the original exception is rethrown;
- The snapshot of the Observer stays untouched during the transaction: the `diff()` at commit is exactly the net change between the last detection before the transaction and now. After a rollback the buffer is back to its content at the start, equal to the snapshot again;
- Events are emitted after the transaction is closed, so writes and transactions in handlers are ordinary ones; an exception thrown by a handler at commit is thrown by `transaction` after all events and `write` are dispatched (see the dispatch below) and does not roll back;
- Node.js runs no other JS code during the transaction, so no other code on the thread can access the ldata and the transaction needs no lock or isolation. `written` is a boolean flag, not a count, because the `write` event carries nothing beyond the ldata.

**Snapshot comparison.** The Observer holds a snapshot as long as the buffer, copied from it at creation. Every write path knows the byte range it wrote and registers it with the Observer (`touch(start, end)`; inside a transaction the ranges accumulate into one); `diff()` compares the buffer with the snapshot byte by byte over the registered range only, as all other bytes are equal by construction, and clears the range. For the bytes that differ it finds the related tags through the lookup table `tags_at_byte`, decodes the old value from the snapshot and the new value from `buffer`, and records a change when the values differ (two NaNs count as equal). It then updates the snapshot and reports all changes together:

- Changes are reported in layout order (a combined word before its bits). For each change Ldata emits `change(tagname, old, new)` first, then the Ltag of that tag emits `change(old, new)`. Events are always emitted after the new value has taken effect;
- Several writes to the same tag between two detections are merged into one event; a value changed and restored emits none;
- When a handler writes a tag again, the nested comparison is only registered; once the current round of changes is reported, another round of comparison runs. If new changes keep appearing for 16 rounds in a row, the rounds stop and the oscillation exception is kept as an error of the dispatch;
- **Dispatch and errors** (spec-data-api.md §4.4). `#written()` and the commit of a transaction own an `errors` array and pass it to `diff(errors)`, then to `emit_all`; nothing in the dispatch throws until the end. `emit_all(emitter, event, args, errors)` (in `dispatch.js`) calls each of `emitter.rawListeners(event)` with `emitter` as `this` inside its own `try`, and pushes what a listener throws; a `once` wrapper of `rawListeners` removes itself as usual. The Observer calls its `report(entry, old, new, errors)` for every change even when one throws, since the changes of a round are collected, and the snapshot updated, before the first is reported. After `diff(errors)` the write emits `write` through `emit_all` as well, and only then throws `errors[0]`, if any. A nested `diff()` (`#diffing`) only records the pending round and pushes nothing. The first exception is thrown as it is, with no wrapper (no `AggregateError`), and the rest are dropped;
- Old values are decoded from the snapshot; no value is cached.

## 6. Byte order conversion

`endian.js` converts between device byte order and the internal big-endian order per compiled entry (`load_entry` / `store_entry` / `io_index` / `io_range`), and builds the byte index table of a whole data block (`io_index_table(block_size, compiled, endian)`), with which a user that exchanges a whole block with a device copies the bytes directly. The package exports none of these functions: the table is built by the layout method `io_index_table(endian)` (§3), which passes the size and the compiled data, and the others are used by `load_tag` / `store_tag` of Ldata (§5), which pass them the private buffer. The table agrees with `load_entry` / `store_entry` for every entry (covered by a test). The functions accept only the byte orders `BE`, `LE`, `BEBS` and `LEBS` (anything else is a `RangeError`, there are no aliases) and do not detect changes:

- 2 bytes: `BE` copies as is; `LE` / `BEBS` swap the two bytes;
- 4 bytes: the four orders `BE`, `LE`, `BEBS` and `LEBS` are supported;
- Bool and single-byte types (Byte, SInt, USInt) read and write one byte without any conversion inside the byte. Their index in the IO buffer is computed per 16-bit register: `byte ^ 1` for `LE` / `BEBS`, `byte` for `BE` / `LEBS`. A Bool changes only its own bit, by bit mask.

## 7. Build and test

- `pnpm build`: `rolldown -c` bundles first, then `tsc -p tsconfig.json` generates the declarations from the JSDoc, also into `dist`. `rolldown.config.js` empties `dist` when it is loaded and exports two configurations, so each entry is bundled on its own with no chunk split: `src/index.js` → `dist/index.js` and `src/dev.js` → `dist/dev.js` (`platform: "node"`, `format: "es"`). `external` is the names of the `dependencies` of `package.json` (and their subpaths) and the built-in modules with the `node:` prefix, so `yaml` stays an `import` in the bundles. `dist/dev.js` keeps the `#!/usr/bin/env node` of its source, and `import.meta` is kept as it is, so `import.meta.main` and `import.meta.filename` refer to the bundle itself;
- Publishing: the `files` of `package.json` are `dist` and `CHANGELOG.md`; the `default` of `exports` and the `bin` point to `dist/index.js` and `dist/dev.js`, and `types` to `dist/index.d.ts` and `dist/dev.d.ts`;
- `pnpm bench`: `bench/change_detection_bench.js` measures reading a block of 86 tags and 146 bytes (loading every tag from a device-ordered buffer, which detects and reports the changes). On a development machine, `load_tag` of every tag in one transaction takes one cycle about 3.1–3.2 µs with no change, 3.1–4.5 µs with a few changes, and 8.5–8.6 µs with every tag changed (each `load_tag` also checks, once, whether an `access` listener exists, which is about 0.6 µs of the 86 tags); copying the bytes with `layout.io_index_table` and one `write_bytes` takes about 0.4 µs, 0.6–1.7 µs and 5.7–5.9 µs;
- `pnpm test`: builds first, then runs the type tests, `node --test` (every test, against `src`) and `pnpm test:dist` (the tests of the bundles); `pnpm lint`: ESLint. There are three kinds of tests:
  - Tests of the internals (`test/*_test.js`, except the bundling test): they use internal modules (the compiled data `COMPILED`, `endian.js`, `reserved.js`, `register_structure` and so on) and run against `src` only; their helpers are in `test/share.js`;
  - Tests of the public interface (`test/api/*_test.js`): they use the public interface only and get the entries under test from `test/api/target.js`, with their helpers in `test/api/share.js`. `target.js` takes the two entries of `src` by default; `pnpm test:dist` runs these tests with `node --test --import ./test/api/dist.js`, where `dist.js` sets the environment variable `LAYOUT_DATA_TEST_TARGET=dist`, so `target.js` imports `layout-data` and `layout-data/dev` by package name, that is the bundles in `dist`. The same tests thus run once against the source and once against the bundles, which are the tests of the bundles. The command line tests run, in both passes, the bundle that the `bin` of `package.json` points to;
  - The bundling test (`test/bundle_test.js`): it checks the bundling itself, that is `exports` and `bin` point to the bundles in `dist`, their exports are those of the entries of `src`, the bundles have external `import`s of `yaml` and `node:` modules only, the run-time bundle has no code of the development entry, and `dist/dev.js` keeps the hashbang.
